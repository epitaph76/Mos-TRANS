# Mos-TRANS — диспетчерский прогноз задержек

Приложение объединяет дашборд из `max-pidor`, регрессию из `xg/catboosts` и вероятность из `ya-dolbayob`. В историческом режиме оно воспроизводит доступную на момент `T` телеметрию, прогнозирует задержку в секундах и вероятность **опоздания более чем на 120 секунд** на целевой остановке. Эта остановка должна иметь плановое прибытие в окне `(T+10 минут, T+15 минут]`. [Проверка по всем требованиям задания](REQUIREMENTS.md) отдельно отмечает реализованное и ограничения.

## TreeSHAP и сценарий дополнительных автобусов

При выборе транспорта в правой карточке сразу под прогнозируемой задержкой
для жёлтого и красного риска с положительным прогнозом показаны четыре
крупнейших вклада признаков TreeSHAP действующего
CatBoost-регрессора. Вклады измеряются в секундах **изменения** задержки
относительно среднего ответа модели; текущее отклонение прибавляется отдельно.
Это объяснение прогноза, а не доказательство причины задержки.

При нажатии на линию маршрута на карте открывается карточка маршрута с кнопкой
«+ Автобус на маршрут». Можно задать число машин на маршруте и время полного
оборота; кнопка добавляет машины в сценарий. Показаны интервал, частота
рейсов и среднее ожидание при равномерном выпуске. Начальные числа — пример.
Сценарий не меняет прогноз задержки уже идущего ТС: в обучающей модели нет
признака размера парка, а данных для причинной симуляции движения нет.

## Источники и границы данных

- Датасет: [раздача организаторов](https://disk.yandex.ru/d/CA6tsj4aJJ4Aaw). Локально нужен `data/dataset.zip`; архив исключён из Git.
- В историческом режиме прогноз строится по `validate/traffic.csv` и `validate/schedule_plan.csv` после каждого пригодного GPS-пакета. `validate/points.csv` больше не ограничивает показанные прогнозы. Пакет доступен только после **обоих** времён: `event_time ≤ T` и `receive_time ≤ T`. Фактические прибытия `time_fact_begin` не попадают в признаки и API.
- Отдельно запускаемый Docker-эмулятор из архива данных посылает бинарные NDTP-пакеты, но его случайная траектория не совпадает с историческим расписанием. Режим NDTP показывает устройство и телеметрию без прогноза, пока нет привязки к маршруту и расписанию.
- Карта браузера показывает плановые остановки и восстановленную по исторической телеметрии геометрию коридоров движения; при отсутствии такого участка используется соединение плановых остановок. Это схема по данным одного дня, а не официальная дорожная сеть. Backend выдаёт последний **уже полученный** GPS-пакет и его время. Между пакетами браузер ведёт маркер по нарисованному маршруту с последней известной скоростью; если маршрут далеко, использует курс. При следующем пакете маркер принимает фактическую координату. Оценка ограничена 30 секундами и не использует будущий GPS для положения ТС или ML-прогноза. В подсказке маркера и разделе «Данные» указан источник показанного положения.
- В карточке исторического ТС отображаются пять предыдущих и одиннадцать следующих плановых остановок. Схема раскладывает их по порядку с равными расстояниями между метками; фактические интервалы времени подписаны в списке, а разрывы от 10 минут выделены отдельно. Метка «плановое время прошло» не означает подтверждённое прибытие.
- В `traffic.csv` нет состояния дверей, а стандартная конфигурация эмулятора не посылает ячейку дверей. Интерфейс явно показывает отсутствие этого сигнала; причина «длительная остановка» не выдаётся за подтверждённую посадку.

## Архитектура

`frontend` (React/MapLibre) → `backend` (FastAPI, replay, TCP NDTP) → `ml` (FastAPI, CatBoost). Backend и ML запускаются в разных контейнерах. В историческом режиме backend упорядочивает пакеты по времени получения, сопоставляет GPS с плановым маршрутом, оценивает текущее отклонение и строит признаки на каждом пригодном пакете. ML загружает прежние модели один раз и возвращает `predicted_delay_s` и `probability_delay_over_120s`. Backend сохраняет успешные прогнозы по ID пакета и целевой остановки; при недоступности ML новые прогнозы временно не рассчитываются, положение ТС продолжает обновляться. OpenAPI: backend на `/docs`, ML на внутреннем `/docs`.

Публичные endpoints backend:

| Endpoint | Назначение |
| --- | --- |
| `GET /api/health` | Готовность и счётчики NDTP |
| `GET /api/replay/snapshot?at=16200` | Срез исторического дня; `at` — секунды от 00:00 6 января 2026 |
| `GET /api/replay/snapshot?at=16200&on_demand=true` | Срез с отдельным расчётом прогноза для режима 1× |
| `GET /api/live/snapshot` | Последнее состояние устройств из TCP-потока NDTP |
| `GET /api/demo/snapshot?at=33600` | Учебный рейс в 09:20 после начала простоя |

Пример точки с прогнозом: `at=16200` (`04:30:00`). Дашборд открывается на первой прогнозной точке. Цвета вероятности: зелёный `<70%`, жёлтый `70–89%`, красный `≥90%`; при отсутствии прогноза показан отдельный статус. Это пороги интерфейса из `src/risk.ts`, не подтверждённые отдельным исследованием стоимости ложных тревог. Причина и рекомендация — объяснение по текущим признакам движения, а не отдельная обученная модель причины. Если признаков недостаточно, карточка так и сообщает.

Для воспроизведения в обычном темпе выберите `1×` на шкале; `3×` ускоряет историческое время втрое. На карте положение обновляется между редкими GPS-пакетами; это визуальная оценка движения, а не новая измеренная телеметрия или вход ML-модели.

Исторический `validate/points.csv` содержит только 151 точку для конкурсного задания. Для дашборда backend создаёт отдельные прогнозные запросы из поступивших GPS-пакетов: выбирает первую плановую остановку в окне `(T+10 минут, T+15 минут]`, принимает GPS не старше 120 секунд и отклоняет сомнительное сопоставление с маршрутом. Карточка обновляется после следующего пригодного пакета и объясняет, почему расчёт недоступен. Нынешние веса модели не менялись; оценка отклонения по GPS отличается от готового `cur_dev_s` в конкурсных точках.

На первом запуске backend сохраняет потоковые признаки в `data/processed_route/stream/`, затем ML-сервис постепенно рассчитывает все пригодные пакеты партиями. Сборка признаков использует только пакет, уже полученный к рассматриваемому времени. На быстром перемещении по шкале прогноз может кратковременно показывать состояние «ответ модели пока не получен». Счётчики `historicalForecastRequests` и `historicalForecastsReady` в `/api/health` показывают ход расчёта.

При скорости воспроизведения **1×** дашборд запрашивает `GET /api/replay/snapshot?at=...&on_demand=true`. Backend приостанавливает фоновый расчёт после текущей партии, использует отдельный кэш и впервые вызывает ML-сервис для текущей доступной точки именно при достижении её курсором симуляции; фоновые прогнозы для ускоренного воспроизведения в этом режиме не подставляются. Если на следующей секунде не появился новый пригодный пакет, повторно рассчитывать ту же точку не нужно. При повторном посещении уже рассчитанной точки используется результат 1×-кэша. На других скоростях фоновый расчёт возобновляется и остаётся прежний режим с предварительно рассчитанными прогнозами. **Признаки для всего исторического архива готовятся заранее при запуске; в режиме 1× по мере воспроизведения выполняется именно ML-инференс.**

Проверка качества в отдельном отчёте (только размеченный test, фактические прибытия используются исключительно для оценки):

```powershell
python -m mos_trans.stream_report --dataset data/dataset.zip --output data/stream-test
```

Отчёт `quality_report.json` содержит абсолютную ошибку текущего отклонения, MAE прогноза по пакетам и MAE последнего прогноза для каждой целевой остановки. В проверенном отчёте: MAE **78,36 с** по 41 239 пакетным прогнозам и **84,51 с** по последнему прогнозу для 4 356 остановок; оценка текущего отклонения доступна для 294 из 353 конкурсных точек и имеет MAE **83,04 с**. Это не новая обученная модель: действующий регрессор получал на обучении готовое отклонение `cur_dev_s`, а потоковый режим оценивает его по GPS. Повторные прогнозы одной остановки зависимы. Вероятность и ранность первого предупреждения в этом режиме пока отдельно не валидированы. Сигнала о дверях в историческом CSV нет; продолжительность посадки по нему не рассчитывается.

## Учебный рейс для оператора

Откройте <http://localhost:5173/?demo=1&autoplay=1> при локальном запуске или <http://localhost:8080/?demo=1&autoplay=1> в Docker. На карте будет одно ТС `130389`, синтетический маршрут из 16 плановых остановок и поток GPS-пакетов каждые 20 секунд. До 09:15 ТС идёт по графику; с 09:15 до 09:22 стоит на остановке, затем движется медленнее и накапливает опоздание. Кнопка паузы, шкала времени и скорость воспроизведения позволяют изучать карточку в любой момент. Удобные срезы API: `at=32700` (09:05, норма), `at=33600` (09:20, простой), `at=34140` (09:29, задержка).

Сценарий создаётся модулем `mos_trans.demo`: `data/demo/scenario.zip` содержит `validate/schedule_plan.csv`, `validate/traffic.csv` и `validate/points.csv`; общие признаки строятся теми же функциями, что и для архивного датасета, после чего backend вызывает те же ML-модели. Запустить генератор вручную: `python -m mos_trans.demo`. Все синтетические точки показаны только в учебном режиме и не входят в `submission.csv`. Вероятность отражает ответ обученной модели на искусственный случай: она не обязана достичь красной зоны и не является проверенной оценкой качества на реальном рейсе.

## Запуск в Docker

Нужен Docker Desktop. Укажите в `.env` путь к архиву на хосте, например на Windows:

```dotenv
DATASET_HOST_PATH=C:/Users/you/Documents/mos-trans/data/dataset.zip
```

Затем из этой ветки:

```powershell
docker compose up --build
```

Дашборд: <http://localhost:8080>. Backend API: <http://localhost:8000/docs>. TCP NDTP: `localhost:9201`. При первом старте backend готовит очищенные таблицы и маршрутные признаки в именованном Docker volume. `dataset.zip` не копируется в образы.

Для локальной разработки без Docker установите `requirements-service.txt` в окружение и выполните:

```powershell
python -m mos_trans.preprocessing --input data/dataset.zip --output data/processed
python -m mos_trans.features.build --input data/processed --output data/processed_route --dataset data/dataset.zip
python -m uvicorn mos_trans.ml_api:app --port 8001
python -m uvicorn mos_trans.backend_api:app --port 8000
npm ci
npm run dev
```

Команды `uvicorn` выполняются в отдельных терминалах. Vite проксирует `/api` на backend. Для генерации плановой карты после обновления данных: `python -m scripts.build_plan --dataset data/dataset.zip`.

## Проверка NDTP-эмулятора

Архив содержит `ndtp-telemetry-emulator.tar`. Извлеките его в локальную папку `data/`, выполните `docker load -i data/ndtp-telemetry-emulator.tar`, затем запустите эмулятор с портом 18080 и доступом к хосту. В `POST http://localhost:18080/api/config` задайте `targetHost: "host.docker.internal"`, `targetPort: 9201`, `units` с уникальными `unitId` и `intervalMs`. Пример конфига и бинарный формат находятся в `docs/Emulator-and-Telematic-Packets-Specification.md` внутри датасета. Backend разбирает handshake и `G6CellNav00`, проверяет CRC и показывает счётчики в `/api/health`.

## CSV для Data Science

Готовый файл: `artifacts/integrated_submission/submission.csv`. Повторить его сборку из общего инференса:

```powershell
python -m mos_trans.submission --features data/processed_route/validate_features.parquet --dataset data/dataset.zip
```

Файл имеет ровно 151 строку, формат `sample_id;prediction`, порядок шаблона организаторов и те же числовые значения, что у финального регрессора `route_delay_trend_submission`. Средняя абсолютная ошибка регрессора на опубликованном test — **55,90 с**; она не является оценкой переноса на другой день. Для вероятности `>120 с` групповой holdout на 13 семействах ТС дал Brier **0,1334**. Датасет охватывает один день, а опубликованные разделы содержат связанные траектории; нельзя трактовать эти числа как проверку на независимом городе или периоде. Абсолютная ошибка доступна лишь на размеченных данных или после фактического прибытия, поэтому текущая карточка её не выдумывает.

Для формы «Загрузка решения» готов текст в `SUBMISSION.md`. Загрузка CSV и заполнение формы выполняются отдельно на платформе; наличие файла в репозитории не означает, что решение отправлено.
