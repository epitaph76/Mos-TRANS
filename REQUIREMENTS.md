# Соответствие заданию и проверенные ограничения

Проверено по коду и развёрнутому Docker Compose 27.09.2026. Статусы означают: **есть** — функция работает в указанном режиме; **частично** — реализована с ограничением из соседней колонки; **нет** — реализация или проверка отсутствует. Историческое воспроизведение и приём живого NDTP — разные режимы.

## Ключевые и функциональные требования

| Требование | Статус | Что подтверждено и чего не хватает |
|---|---|---|
| Предупреждение строго за 10–15 минут до события | **Частично** | `stream_forecast.py` и `inference.py` допускают целевую остановку с **плановым** временем прибытия в `(T+600 с, T+900 с]`. Время первого возникновения задержки не размечено; нельзя утверждать, что тревога появляется за 10–15 минут именно до него. ТС может уже отставать в момент `T`. |
| Независимые Backend и ML-модуль | **Есть** | FastAPI `backend_api.py` и `ml_api.py` работают в отдельных контейнерах; Backend обращается к ML по HTTP. Код обучения и инференса расположен отдельно в `mos_trans/modeling` и `mos_trans/inference.py`. |
| Непрерывный приём NDTP и исторических данных | **Частично** | `ndtp.py` принимает TCP-пакеты handshake и `G6CellNav00`, проверяет CRC; `stream_forecast.py` обрабатывает архивные CSV. Отдельный CLI подаёт записанные рейсы через NDTP и заранее регистрирует их планы. Поддержан используемый поднабор протокола, не все типы NDTP-сообщений. |
| Сопоставление GPS и скорости с расписанием | **Частично** | Исторические GPS привязываются к плановой последовательности через `RouteMatcher`; настроенный живой рейс также получает оценку отклонения по уже поступившим GPS. Для 37 рейсов без плана показывается только положение. Автоматическое получение обновлений оперативного расписания не реализовано; в CSV нет состояния дверей. |
| Очистка и производные признаки | **Есть для исторических данных** | `preprocessing/core.py` очищает скорость и GPS, проверяет `event_time ≤ T` и `receive_time ≤ T`; рассчитываются скорости, доля остановок, возраст данных, контекст соседних ТС. `stream_forecast.py` дополнительно оценивает длительность простоя и среднюю скорость участка. Контракт полей — [FEATURES.md](FEATURES.md). |
| Вероятность задержки через 10–15 минут | **Частично** | Ансамбль CatBoost выдаёт вероятность опоздания на целевую остановку **строго более 120 с**; регрессор выдаёт ожидаемую задержку в секундах. Для настроенных NDTP-рейсов backend вызывает тот же ML-сервис. Отдельная калибровка на потоковых запросах и новых днях не проведена. |
| Абсолютная ошибка прогноза | **Есть при известном факте** | `stream_report.py` считает абсолютную ошибку после получения фактического прибытия. На опубликованном test конкурсный регрессор имеет MAE 55,90 с; отдельная потоковая проверка дала MAE 78,36 с по 41 239 пакетным прогнозам и 84,51 с по последнему прогнозу для 4 356 остановок. Онлайн до прибытия истинная абсолютная ошибка неизвестна и не показывается. |
| Выявление паттерна и причины | **Частично** | `backend_api.explanation()` отмечает длительную остановку, медленный соседний поток, снижение скорости и накопленное отставание. Это наблюдаемые эвристики, не обученная диагностика причин. TreeSHAP в `inference.py` объясняет вклад признаков в прогноз, но не доказывает причинность. |
| Карта маршрутной сети и текущих ТС | **Есть** | `TransportMap.tsx` показывает исторические коридоры и живые NDTP-маркеры. В NDTP-режиме линия строится из плановых остановок настроенного рейса; у рейса без плана остаётся GPS-маркер. Между пакетами положение маркера оценивается, будущие координаты не передаются в прогноз. |
| Зелёный/жёлтый/красный риск | **Есть** | `src/risk.ts`: зелёный при вероятности `<70%`, жёлтый при `70–89%`, красный при `≥90%`; отсутствие прогноза имеет отдельный статус. Пороги интерфейса не оптимизированы по цене ложной тревоги и пропуска. |
| Карточка инцидента и рекомендации | **Есть с ограничением** | Карточка показывает ТС, вероятность, прогноз секунд задержки, плановую целевую остановку, участок, наблюдаемый паттерн и предложенное действие. Рекомендации эвристические; их эффект не оценён на данных. |

## Общие и нефункциональные требования

| Требование | Статус | Что подтверждено и чего не хватает |
|---|---|---|
| Python 3.12+, CatBoost, PyTorch | **Частично** | Docker-образы используют Python 3.12 и CatBoost. Модели PyTorch нет; стек в задании рекомендательный. |
| Docker-контейнеры | **Есть** | `docker-compose.yml` собирает `frontend`, `backend`, `ml`; локально проверен запуск всех трёх. Архив `dataset.zip` монтируется с хоста и не находится в Git. |
| OpenAPI и документация по коду | **Частично** | FastAPI генерирует `/docs` и `/openapi.json` у Backend и ML. Отдельной сгенерированной PyDoc/Sphinx-документации нет; `README.md` и [FEATURES.md](FEATURES.md) описывают запуск и контракт данных. |
| Низкая задержка предиктов | **Не подтверждено измерениями** | ML принимает партии до 256 точек, модель загружается один раз. Репозиторий не содержит воспроизводимого нагрузочного теста с p50/p95 latency, пропускной способностью и числом одновременных ТС. |
| Обрыв связи и деградация | **Частично** | При недоступности ML Backend продолжает показывать положение и доступный последний прогноз с признаком устаревания. При обрыве NDTP последняя позиция видна ограниченное время. `/api/health` проверяет состояние Backend и счётчики, но не подтверждает доступность ML; персистентной очереди для пропущенных NDTP-пакетов нет. |
| Дообучение и масштабирование инференса | **Частично** | Сохранены скрипты подготовки/обучения, ML выделен в отдельный сервис. Версионирование модели, автоматическое дообучение, проверка нового периода и горизонтальное масштабирование с общим состоянием не реализованы. |
| GPU | **Нет; дополнительная возможность** | Обучение и инференс используют CPU. GPU не обязателен для действующих табличных CatBoost-моделей. |

## Дополнительные фичи

| Фича | Статус | Граница реализации |
|---|---|---|
| Map Matching | **Частично** | Backend выбирает участок плановой последовательности остановок с учётом расстояния, времени и предыдущего продвижения; повторные коридоры проверены тестом. Отдельные скрипты строят сеть для отображения. Привязки прогноза к официальной дорожной геометрии и полноценного вероятностного map matching нет. |
| What-if: дополнительное ТС | **Есть как упрощённый сценарий** | `WhatIf.tsx` рассчитывает интервал, частоту и среднее ожидание при равномерном выпуске. Сценарий **не** пересчитывает пробки, движение других ТС или вероятность задержки текущего рейса. |
| ONNX, TensorRT, квантование | **Нет** | Применяется обычный CatBoost-инференс; оптимизация формата модели и сравнительный latency-бенчмарк не выполнены. |
| Ансамбль CatBoost + PyTorch/Transformer | **Частично** | Вероятность выдаёт ансамбль CatBoost-моделей; регрессор тоже CatBoost. Нейросетевой последовательной модели и смешанного ансамбля нет. |

## Приоритетные следующие шаги

1. Подключить источник оперативного расписания для настоящих NDTP-устройств: сейчас привязка `unitId` к рейсу передаётся внешним CLI или через API вручную.
2. Ввести и разметить момент возникновения новой задержки, измерить фактическое опережение первой тревоги, recall, precision и число ложных тревог на рейс.
3. Проверить MAE и калибровку вероятности на независимых днях и в потоковом режиме, затем выбрать пороги риска по условиям работы диспетчера.
4. Измерить p50/p95 latency и поведение при потере ML/NDTP под нагрузкой; добавить наблюдаемость и механизм восстановления пропущенных событий.

Отсутствующее состояние дверей, влияние выпуска резервного ТС и качество на новых днях нельзя подтвердить по имеющемуся архиву без дополнительных данных.
